## ⚠️ P1(强烈建议本里程碑内改)

### P1-1 NL 查数安全闸:逗号连接(comma-join)可绕过白名单
- 文件:`backend/.../ai/service/NlQueryService.java:44-45`(TABLE_REF 正则)、`:162-175`(闸1)
- 人话:安全闸靠正则 `(?:from|join)\s+(表名)` 找表名逐个查白名单。但 SQL 允许用逗号连表:
  `SELECT * FROM v_ai_loss, yc_vend_user`。正则只抓到 `from` 后面第一个 `v_ai_loss`(在白名单),
  逗号后面的 `yc_vend_user` 前面既没有 `from` 也没有 `join`,**正则根本不看它** → 闸放行,
  最终执行成对 `yc_vend_user` 的交叉连接,把业务表(含用户表)字段读出来。子查询/JOIN 形式都能被抓
  (因为带 from/join 关键字),唯独逗号连表是漏网。
- 现状缓解:当前 `ask()` 永远用硬编码模板 SQL,用户问题只用来选模板、不拼进 SQL,所以**今天打不穿**。
  但代码注释与测试都把 `enforceSafety` 当作"LLM 生成 SQL 也照过的可信闸"来宣传;一旦接真网关做
  text2SQL(设计就是为这天准备的),这条立刻变 P0。`AiFamilyTest` 也没覆盖逗号连表用例。
- 修法:不要用正则数表名(黑名单思路必漏)。改成**白名单式解析**:
  ① 用真正的 SQL 解析器(JSqlParser)取出所有表引用(含逗号 FROM 列表、子查询、CTE),逐个比对白名单;
  ② 或更稳:禁止逗号连表和裸多表 FROM,只允许"单表 + 显式 JOIN 白名单视图",其余一律拒;
  ③ 补一条 `SELECT * FROM v_ai_loss, yc_vend_xxx` 必被拒的测试。

### P1-2 异常归因 explain 全盘信任客户端传来的数字与幂等键
- 文件:`backend/.../ai/interfaces/AiController.java:113-117`、`ai/service/AnomalyService.java:69-93`
- 人话:`POST /v1/ai/anomalies/explain` 直接 `@RequestBody AnomalyService.Anomaly`,把整条异常
  (含 `key` 和 `metrics` 里的所有数字)当输入。服务端**不重新侦测、不校验**,直接把这些数字塞进
  给 LLM 的 prompt、塞进 `inputDigest` 落库,还拿客户端传的 `key` 当幂等键。后果两条:
  ① 违反本项目"数字全部来自规则引擎、LLM 永不碰数"的铁律——客户端能编一组假数字,拿到一段
     以假为真的 AI 归因,并作为"可追溯过程"存进 `llm_call_log`;
  ② 幂等键由客户端控制 → 可用真异常的 key 配假 metrics 先污染当日缓存,之后正常调用(force=false)
     命中被污染的结果(缓存投毒)。
- 背景:这是内网单店 ERP,利用门槛低但危害有限;仍建议修,因为它直接戳穿了"透明四件套可信"的地基。
- 修法:explain 只接 `key`(或 anomalyId),服务端**用 key 重新 `detect()` 定位那条异常、用服务端算出的
  metrics** 去起草;幂等键在服务端由 scene+重算后的 key 拼,不吃客户端字段。

## 💡 P2(可改可不改)

### P2-1 安全闸还漏 `#` 注释 + 不封顶 LIMIT
- `NlQueryService.java:153`、`:177-179`。只挡了 `--` `/*`,没挡 MySQL 的 `#` 行注释;
  且"强制 LIMIT"只判断有没有 `limit` 这个词,不校验数值——LLM 可生成 `LIMIT 99999999`。
  `SELECT ... FROM v_ai_month_gross #` 还会把后面自动追加的 ` LIMIT 200` 整段注释掉,失去限流。
- 修法:注释符统一挡 `-- / /* / #`;LIMIT 存在时校验并夹到 `MAX_LIMIT` 上限。

### P2-2 网关缓存把"降级"结果当天复用 + 无并发去重
- `LlmGateway.java:166-172`。`findCached` 只排除 `失败`,`降级`(LLM 挂了用规则草稿)会被缓存整天,
  哪怕 LLM 当天恢复也不再重试(force 才刷)。另外 invoke 没有 §4.19 要求的"同内容 5s 双击/并发去重",
  两个并发同 key 请求会各调一次真网关、各插一条 log(接真 key 后 = 重复烧钱)。
- 修法:降级结果给更短窗口或不缓存;真网关接入前补一个基于 idemKey 的短锁/唯一约束。

### P2-3 透明四件套接口无归属校验
- `LlmTransparencyService.java:24` / `AiController.java:137`。`GET /transparency/{id}` 按自增 id 直取,
  可枚举他人调用记录。内网单店影响小,记一笔。

### P2-4 action_item 无乐观锁,回查/编辑并发有竞态
- `ActionItem.java`(无 `@Version`)、`ActionItemService.recheck:157` / `update:82`。并发回查+编辑
  同一条会互相覆盖。单人使用概率低,量产多人前建议加 `@Version`。

### P2-5 导出下载用裸 `<a href>` GET,不带鉴权头 + month 未编码
- `frontend/src/api/monthly.ts:189-209`。锚点 GET 不走 axios 拦截器,若鉴权是请求头 token 则导出会 401
  (cookie/session 则没事);`?month=${month}` 未 `encodeURIComponent`。后端 `MonthlyController.safeMonth`
  也只是原样透传 month(文件名侧已 URL 编码,无 CRLF 注入风险)。属功能健壮性,非安全。
- 修法:导出改 axios `responseType:'blob'` 走统一鉴权;month 前端 `encodeURIComponent`。

### P2-6 盘亏一键起草可重复落库
- `ActionItemService.draftFromStocktake:238` + `create:66`。同一盘点单同一原因反复确认会建多条改进任务;
  `resp.existing` 只在 UI 提示,服务端无唯一约束兜底。建议 create 时按 (refType,refId,metricKey,metricParam)
  查重或加唯一索引。

## ✅ 做得好的地方(交叉验证通过)

- **LLM 零参与算数**:Insight/Anomaly/Monthly/Pdca/Nl 的数字全部来自规则引擎/SQL 聚合,LLM 只把
  已算好的"草稿"润色成人话(`MockLlmService` 只回显 `草稿:` 行)。`PdcaMetricService` 所有除法都有
  `total==0 / prev.signum()==0` 守卫,无除零。
- **mock 断路双保险**:`RoutingLlmService` 按 `isConfigured()` 分流去 mock;`OpenAiCompatLlmService`
  的 `chat/chatVision` 入口再各硬校验一次 `isConfigured()` 才可能发网络请求。`Scenario20` 断言
  `getRequestCount()==0` 且六挂点各落 ≥1 条 log,零外呼有真实证据。
- **置信分真算**:0.90/0.40/0.30 按数据完备度(有无销售/是否空月/数据行数)计算,非写死单值。
- **每次调用都落库**:所有 AI 服务经 `LlmGateway.invoke/record`,非缓存命中即插一条四件套 log。
- **只读边界干净**:bi、monthly 两模块全量扫描无任何 insert/update/delete。
- **前端无 XSS**:全仓无 `v-html`,用户 NL/SQL/AI 文本一律走 `{{ }}` 文本插值自动转义;
  下载 `Content-Disposition` 文件名已 URL 编码,无头注入。
- **无硬编码密钥**;`CREATE OR REPLACE VIEW` 迁移幂等、视图仅 SELECT 且过滤 `is_deleted`。
- **月报一致性**:七件套口径月统一由利润表解析,Excel/Word 与 API 同源,空月各节有兜底文案。

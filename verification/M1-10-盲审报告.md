## 🛑 P0(必修才能上线)

### P0-A 两人同时确认同一张单 → 库存记两遍账(并发双过账)
- **位置**:`backend/src/main/java/top/aole/vend/modules/doc/service/DocService.java:161-213`(confirm)、`:245-255`(markRedFlushed)、`:286-293`(transition)、`RedFlushService.java:152-203`(execute)
- **人话**:确认单据的流程是"先读单据看状态 → 再改状态 → 再记库存流水"。就像两个人同时看到货架上贴着"待确认",各自撕下来贴"已确认"——数据库不会拦第二个人,`updateById` 是无条件覆盖。结果:**同一张单的库存/成本被过账两次**,账就错了。双击确认按钮、两人同时点、红冲同一张单,都能触发。这是记账系统,账错一次找一天。
- **建议修法**:状态流转改成**条件更新**——`UPDATE yc_vend_doc_head SET doc_status=新 WHERE id=? AND doc_status=旧`,受影响行数=0 就抛"该单已被他人处理";或给 doc_head 加 MyBatis-Plus `@Version` 乐观锁。一处封装在 transition/confirm 里,全系统受益。

### P0-B 上传文件名可带路径 → 归档时写到任意目录(路径穿越)
- **位置**:`ImportService.java:205`、`InitialImportService.java:769`——`new File(storageDir, batch.getId() + "/" + pending.getFileName())`,且 `FileUtil.move(tmp, archive, true)` 是**覆盖写**
- **人话**:归档路径直接拼了客户端传来的原始文件名。文件名如果是 `../../app.jar` 这种,文件就会被搬到存储目录**外面**、还能覆盖同名文件——等于任何能访问接口的人可以往服务器任意可写位置放文件/覆盖文件。SSO 接上也防不住(登录用户照样能传)。
- **建议修法**:一行事——归档前 `FileUtil.getName(pending.getFileName())` 只取纯文件名(再兜底把 `/ \ ..` 换掉),或干脆用 `batchNo + ".xlsx"` 当归档名、原始文件名只存数据库字段。

## ⚠️ P1(上线前修)

### P1-1 导入确认没有事务,中途崩溃批次永远卡在「处理中」
- **位置**:`ImportService.java:182-239`(confirm 方法没有 @Transactional;批次状态只有 处理中→已导入/已回滚 两条路)
- **人话**:导入 5000 行到第 3000 行时断电/重启,批次状态停在「处理中」——而回滚接口只认「已导入」,这批就既回不了也标不完,成了僵尸批次。行级去重虽然让重新导入不重复,但僵尸批次会永远躺在列表里。
- **建议修法**:confirm 主体套 try/finally,失败把批次标成「失败」并允许对「处理中/失败」批次做回滚清理;或提供"批次修复"入口。

### P1-2 锁账期红冲的「老板越权」谁都能点
- **位置**:`DocController.java:58`(bossOverride 是请求体布尔,后端不查任何角色)对比 `PeriodController.java:46-49`(解锁至少还查 X-User-Role 头)
- **人话**:同样是老板特权,解锁要出示"老板"工牌(虽然工牌是自己写的),锁账期红冲连工牌都不用看——传个 `bossOverride: true` 就放行。占位归占位,两处的门槛应该一致,否则 SSO 接入时容易漏掉这个口子。
- **建议修法**:redFlush 接口同样读 X-User-Role 头并传给 service 校验(和 unlock 一个模式),SSO 接入时统一替换。

### P1-3 负库存拦截是"先看再写",并发下两单同时透支
- **位置**:`StockLedgerWriter.java:33-43`(sumWarehouse 查完再 insert,中间没锁)
- **人话**:库存剩 10,两张各出 8 的单同时确认——两边查的时候都看到 10,都觉得够,双双放行,结果 -6。修完 P0-A 后同一张单不会双过账了,但**两张不同的单**并发仍有此洞。
- **建议修法**:出库过账前对该商品加行锁(如 `SELECT id FROM yc_vend_product WHERE id=? FOR UPDATE`),把"查余额+写流水"串行化;单机小并发下代价可忽略。

### P1-4 预挂单被作废时,仓库侧锁定的货不会放回来
- **位置**:`DocService.java:139-141`(voidDoc)+ `DocStateMachine.java:46`(预挂单→已作废 是合法流转);对照 `StockService.matchPendingTransfer:196-200`(冲抵路径有 +qty 释放,voidDoc 没有)
- **人话**:手工预挂单确认时仓库已经扣了货("只锁仓库侧")。导入冲抵作废时会把货加回去,但如果哪天通过 voidDoc 直接作废预挂单(服务方法是 public 的,M2 一旦加"作废"按钮就会踩),货就永远扣着,单据却显示已作废——账实分离。当前 M1 没有外部入口,属于埋着的雷。
- **建议修法**:voidDoc 里加守卫:状态为预挂单的单据禁止直接作废(提示走冲抵/转正),或作废时自动反向释放仓库流水。

### P1-5 docSource 由客户端指定,"导入"特权可被冒领(潜伏)
- **位置**:`DocCreateReq.java`(docSource 字段)+ `DocService.createDoc:86`(直接信任入参)
- **人话**:单据来源="导入"自带三大特权:免预挂单、免碰撞检查、可豁免负库存。现在 M1 没有开放通用建单接口所以踩不到,但 createDoc 信任入参的写法留着——M2 单据中心一旦开建单 API,伪造"导入"就把 P0-4"转移单唯一生产者"整条防线绕穿。
- **建议修法**:公开入口一律强制 SOURCE_MANUAL(像 PurchaseReceiptService.toDocReq 那样写死),"导入"来源只允许 ImportService 内部设置;DocCreateReq 对外 DTO 去掉 docSource。

### P1-6 【已知悉·边界条款】X-User-Name / X-User-Role / user_id=0 全部可伪造
- **位置**:`Operators.java`、`PeriodLockService.java:37-38`、各 Controller 的 `UID=0L`
- **人话**:知悉这是 SSO 接入前的占位方案,此处只钉边界:**接 SSO 之前,本系统等于不设防**——经手人随便填、老板角色随便冒、op_log 留痕可栽赃。必须保证服务只在内网/仅老板娘电脑可达;SSO 接入时按 grep `X-User-|UID = 0L|IMPORT_USER` 清单逐处替换,别漏。

## 💡 P2(记债,不阻塞)

1. **单号生成并发撞车**:`DocService.java:332-338` count+1 拼流水号,并发建单撞 uk_doc_no 唯一键,用户看到"系统繁忙"。修法:捕获重复键重试一次,或改 MySQL 自增序列表。
2. **未知订单类型静默算"正常"**:`ImportService.java:845-859`——厂家后台哪天新增"赠品订单",全被记成正常营收。修法:不认识的类型记 import_error 警告而不是默认放行。
3. **金额未统一 setScale 就落库**:`DocService.java:303-309/321` qty×unitPrice(12,3×12,4=7位小数)直接落 decimal(12,2),靠 MySQL 静默四舍五入,头表合计与 Σ 明细可能差一分。修法:入库前统一 `.setScale(2, HALF_UP)`。
4. **导入落的 cost_amount 是"全期平均"不是"移动加权"**:`ImportService.java:861-875`(weightedCost)与 CostEngine 口径不同;报表读的是引擎实时重放所以展示正确,但 sale_record 快照要等手动"成本重算回写"才对齐,M3 结算取数前必须刷。修法:导入完成后自动触发 recalc,或落库时就用引擎口径。
5. **转移单冲抵失败会把已入账的行标成"失败"**:`ImportService.java:453-473` catch 范围把 confirm 之后的 matchPendingTransfer 也包进去,单已确认过账、错误表却说"转移单生成失败",误导排查。修法:缩小 try 范围,冲抵失败单独记。
6. **op_log JSON 手拼**:`PeriodLockService.java:86` 用字符串拼 JSON,备注里带引号会拼出坏 JSON。修法:统一 JSONUtil。另 `CostAdjustService.java:135` 魔数 490 截断备注,建议常量化。
7. **暂存文件/内存 Map 无清理**:`ImportService.java:131/169` 上传后不确认的 tmp 文件与 pendingUploads 条目永不回收。修法:启动时清 tmp 目录 + 条目带时间戳过期。
8. **application.yml 默认 DB 密码 vend123 明文**:开发默认可接受,部署时务必 ENV 覆盖并确认 3308 端口不对外。

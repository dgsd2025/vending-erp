## 🛑 P0(必须修,阻塞提交)

### P0-1 付款确认无并发抢占 + 不复核结算单当前状态 → 双笔流水 / 给已红冲的采购付钱
**文件**:`vending-erp/backend/src/main/java/top/aole/vend/modules/settle/service/PaymentService.java:102-158`

**人话**:确认付款是"先读状态再干活"(check-then-act):第 105 行读到`待付款`就一路往下走,最后才 updateById。两个问题:

1. **双击/两人同时确认同一张付款单**:两个请求都读到`待付款`→ 都通过 → 都发 MoneyPostingEvent → **cash_flow 落两笔"供应商付款"支出,账户余额被双扣**(应付余额倒是只算一次 payment 行,于是钱账和应付对不上)。注释写着"重复确认被拒,幂等"——只对串行双击成立,并发窗口不成立。同文件里 SettlementService.confirm(SettlementService.java:192-199)已经用条件更新抢占(`待核对→核销中`)做对了,付款单这个**全系统最高频的动钱操作**反而没有。
2. **确认时不看结算单现在是什么状态**(132-151 行只比金额):时序 = 建付款单(待付款)→ 采购单被红冲 → 结算单被连锁**作废** → 用户再点"确认付款":没有任何拦截,钱照付、**已作废的结算单被改成"已完成"复活**、还会尝试推采购单状态。等于给已退货的采购付了钱。

**修法**:
- 抢占:仿照 SettlementService,确认入口先 `UPDATE payment SET pay_status='确认中' WHERE id=? AND pay_status='待付款'`,受影响行数≠1 直接抛"已被他人处理";或最低限度用 `LambdaUpdateWrapper.eq(payStatus, 待付款)` 条件更新做最终状态落库,失败回滚整事务(事件是同事务的,会一起回滚)。
- 复核:确认时重查 bill,`bill_status` 不在 `待付款/差异挂起` 一律拒绝(尤其是`已作废/已完成`),提示"结算单已被红冲/已核销,请作废本付款单"。

### P0-2 索赔到账 / 支出确认 同样是 check-then-act → 并发双记直接翻倍利润表其他收入/杂费
**文件**:
- `vending-erp/backend/src/main/java/top/aole/vend/modules/claim/service/ClaimService.java:129-170`(receive)
- `vending-erp/backend/src/main/java/top/aole/vend/modules/expense/service/ExpenseService.java:107-153`(confirm)

**人话**:和 P0-1 同病:132/110 行读状态`申请中`/`待确认`,通过后发事件落流水,最后 updateById 收状态。两个并发请求都能通过 → **索赔到账落两笔 CLAIM_INCOME(其他收入-赔付翻倍)/ 支出落两笔(杂费翻倍 + 设备台账插两行)**。这两处直接污染利润表行,比付款(NON_PL)后果更显性。M3 五个动钱确认点里,只有 结算单(M3-3)、资金调整(走 DocStatusGuard)、钱盘收口(条件更新)做了抢占,付款/索赔/支出三个漏了——同一里程碑内纪律不一致,说明不是设计取舍而是遗漏。

**修法**:统一抽一个"条件更新抢占再干活"的小模式(或直接学 CashCheckService.finish:258-267 的写法),三处各加一行条件更新:`WHERE claim_status='申请中'` / `WHERE exp_status='待确认'`,受影响 0 行抛 BizException。测试各补一例"先确认成功后,旧页面再点确认必须被拒"。

### P0-3 采购类导入整批回滚不查应付链 → 结算单(甚至已付款)悬空存活,可为不存在的货继续付款
**文件**:`vending-erp/backend/src/main/java/top/aole/vend/modules/imports/service/ImportService.java:636-688`(rollback docLike 分支)
**关联**:`settle/service/SettleBillGenerator.java:33-45`、`InitialImportService.java:369,390`

**人话**:M3-2 上线后,**采购入库单确认会自动生成 settle_bill**(期初采购导入建了供应商、走 docService.confirm、事件 phase=FULL,同样会生成)。但导入中心的整批回滚 blockers 还是 M2 的两条(被红冲引用 / 冲抵过预挂单),**完全不知道应付链的存在**:回滚会把采购单特权作废、删库存流水,而它的结算单原样留下——
- 结算单还在`待确认/待付款`:老板照样能复核、带抵扣、付款(SettleBillService.confirm 里 `docStatus==CONFIRMED` 才推状态,VOID 就跳过,**不报错继续走**)→ 为一批已经"不存在"的货付了真钱;
- 若已付款:采购从应付余额公式里消失(作废状态不在 CONFIRMED_STATES),付款/抵扣还在 → 供应商余额凭空变成大额"预付款",对账单期末数失真。

销售侧回滚拦"已被结算单核销"拦得很好(619-630 行),采购侧是漏网。

**修法**:docLike 回滚前加第三类 blocker:`SELECT ... FROM yc_vend_settle_bill WHERE source_doc_id IN (docIds) AND bill_status NOT IN ('已作废')`——
- 有已付款/已完成/差异挂起的 → 拒绝回滚,提示"先走红冲连锁(它会正确处理应付红字)";
- 只有待确认且无付款的 → 允许回滚但同事务把结算单作废+释放抵扣(直接复用 SettleBillService.onPurchaseRedFlush 的未付款分支逻辑)。
补一条回归测试:期初采购导入 → 结算单生成 → 回滚 → 断言结算单已作废/或回滚被拦。

## ⚠️ P1(强烈建议 M3 内修)

### P1-1 钱盘"平台到账核对"行对着一个恒为 0 的数
**文件**:`stocktake/money/service/CashCheckService.java:100-108` + `money/service/AccountService.java:117-144`

**人话**:平台待结算是虚拟账户,其"余额"在钱盘里取的是 `AccountService.list()` 的 期初+Σcash_flow。但**全系统没有任何一处往虚拟账户写流水**(销售不落流水;结算划转只给真实账户落毛额收+手续费支)——这个账户的流水余额永远是期初(通常 0)。而总览/资产快照里的"平台待结算"是从 sale_record 算的(SettlementQueryMapper.pendingBalance)。同一个概念两个数,钱盘核对页给老板看的是错的那个。
**修法**:钱盘 ② 平台行的系统数改调 `SettlementQueryMapper.pendingBalance()`(PLATFORM 模式),不要用虚拟账户流水余额;或者干脆此行只读展示 pendingBalance + 跳转结算单页。

### P1-2 应付余额"双口径":钱盘应付核对 vs p8 供应商卡 公式不同,会算出两个数
**文件**:`stocktake/money/mapper/CashMoneyQueryMapper.java:24-38` vs `settle/service/PayableService.java:67-103`

**人话**:p8/资产快照用 §7.3 正式公式(期初+Σ已确认采购−退货−抵扣−付款);钱盘应付行自己另写了一套(期初+Σ结算单实结净额−Σ付款),差异点至少四个:
1. **不筛 bill_status**——`已作废`的结算单也被 SUM 进净额(红冲连锁作废后,钱盘还按它算应付);
2. **红字双扣**——红字被冲抵时下一张正常单的 amount_actual 已经减过了,SQL 又把红字整额再减一次;
3. **漏了退货**(退库单不产生结算单,正式公式里有 −退货,这里没有);
4. **付款口径不同**——这里按 `pay_status IN ('已付款','结算完成')`,正式口径按 `pay_time IS NOT NULL`(差异挂起也算已付)。
后果:老板月度钱盘看到的"系统应付"和供应商卡不一致,会被引导去做不该做的"补录/红冲"。这正是全局铁律 §4.17/§4.24(单一真相源)要防的事。
**修法**:删掉这份 SQL,钱盘应付行直接调 `PayableService.overviewOf()`(注释里说"不碰并行票 Java 代码"是开发期的票面边界,合仓后应当收敛);至少也要补 status 过滤 + 退货项 + 统一付款口径,并加一条断言两口径相等的集成测试。

### P1-3 finreport 取数 SQL 漏 `is_deleted=0`,与"待结算口径别处不许另抄一份"直接打架
**文件**:`finreport/mapper/FinReportQueryMapper.java:28-36,48-51,62-65` vs `settlement/mapper/SettlementQueryMapper.java:22`

**人话**:SettlementQueryMapper 把口径写死成常量并注释"别处不许另抄一份",结果 FinReportQueryMapper 抄了一份还抄丢了 `is_deleted=0`(和 `offline_flag=0`)。这些是手写 @Select,MyBatis-Plus 的逻辑删插件**不会**自动加过滤。当前销售回滚是物理删所以暂时没炸,但 sale_record 实体带逻辑删字段,未来任何软删路径(手工修数、新功能)都会让**资产快照/利润表吸入已删除的销售**。`salesByBookPeriod` 同样裸查。
**修法**:三条 SQL 补上 `AND is_deleted=0 AND offline_flag=0`(或直接 import 复用 `SettlementQueryMapper.SETTLE_SCOPE` 常量,真正做到只有一份)。

### P1-4 利润表"成本调整"“其他收入-补贴”两行永远是 0——喂数的类别没有任何写入方
**文件**:`money/domain/enums/CashFlowCategory.java:44-45,28-29` + `finreport/service/ProfitReportService.java:128-131,154-155`
**佐证**:全仓 grep `COST_ADJUST_FLOW|EXCHANGE_SUBSIDY|SHRINK_LOSS|SALE_INCOME|SALE_COST|ACCOUNT_TRANSFER` 除枚举定义外零引用。

**人话**:利润表的"成本调整"行从 `pl_line=成本调整` 的流水聚合取数,但 M1-7 说好"已售部分 M3 实装"的那笔流水,M3 没接线——成本调整单确认只动 stock_ledger(未售部分),**已售部分的利润修正至今进不了利润表**,而报表上这一行看着像"0=没有调整",给人假安心。同理"其他收入-补贴"行:补贴走的是抵扣确认单(冲应付,不落现金流水),这一行也恒 0——但补贴对冲兑换成本的经济收益于是**在利润表上完全不体现**(采购全额进成本,抵扣只减付款)。损耗行的 `shrinkFlow` 兜底同样永远是 0(无写入方,当前无害)。
**修法**:①成本调整单确认时对"已售部分Δ"发 MoneyPostingEvent(COST_ADJUST_FLOW)——注意它没有现金动作,需要评估是挂到某真实账户还是给写手开"非现金行"通道(建议后者:加 `cashless` 标记不进账户余额、只进 pl_line);②补贴行:要么在抵扣"已抵扣"时落一笔非现金 EXCHANGE_SUBSIDY 收入,要么把利润表该行改为直接取 `deductionTotalByStatus('已抵扣')` 并注明口径;③把"枚举类别必须有写入方或标注 reserved"写进 M3 的完备性测试。

### P1-5 结算差异收口后,差额从所有报表里"蒸发"
**文件**:`settlement/service/SettlementService.java:209-258,288-303`

**人话**:PLATFORM 确认时不管两差多大都会回填+落流水(设计如此),差异挂起→resolveDiff 只补一句说明就收口。此时:漏单差/扣款差对应的钱(平台吞货、多扣款)——不在待结算(已回填清空)、不在现金(只到账了实际额)、不进利润表(没有任何损耗/支出流水)。**平台吞掉的钱在净资产里凭空消失且利润虚高**,只剩 op_log 里一行字。
**修法**:resolveDiff 时按核实结论给一个出口:核实为"平台多扣/吞货"→ 落一笔 SHRINK_LOSS(或新类别"平台扣款损失",pl_line=损耗/杂费)流水挂在结算单上;核实为"我方漏单"→ 指引补录销售。至少要在利润表加一行"结算差异损失"。

### P1-6 红冲已(部分)付款的采购后,原结算单不关闭,剩余额还挂着"待付款"
**文件**:`settle/service/SettleBillService.java:179-221`(已付款分支只建红字,不动原单)

**人话**:实结 1000、已付 400(差异挂起)时红冲采购:生成 400 红字、释放抵扣,但原结算单还停在`差异挂起/待付款`,页面上剩余 600 看起来仍然该付——货都退了。配合 P0-1(付款确认不复核结算单状态)就是真金白银付出去。
**修法**:已付款分支同时把原结算单置为终态(建议`已作废`或新状态`已红冲关闭`,diff_note 说明"原采购红冲,已付部分由红字 JS-xxx 承接"),并拒绝再关联新付款。

### P1-7 结算模式切换无老板角色守卫
**文件**:`money/interfaces/MoneyController.java:152-158` + `money/service/SettleModeService.java:63-83`

**人话**:结算模式是全系统钱账口径的总开关(切换后旧单要作废重录、资产快照第②项直接清零/出现),但 PUT /settle-mode 任何操作员都能调;而资金调整、结算单复核这些影响小得多的动作反而要老板头。防呆等级倒挂。
**修法**:`settleModeService.set` 前加 `periodLockService.assertBossRole(role, "结算模式定型")`,前端设置页同款"我是老板"复选框。

### P1-8 结算单复核确认无抢占:同一张待抵扣可被并发双用
**文件**:`settle/service/SettleBillService.java:82-147`

**人话**:确认结算单时对每张抵扣先 selectById 再判`待抵扣`(96-110 行),两张结算单并发确认(或同一张双开页面)都能通过校验,双双把同一张抵扣的金额从各自实结里减掉——供应商少收两次钱,而应付余额公式里抵扣只减一次,账就歪了。老板单人操作概率低,但和 P0-1/P0-2 是同一类病。
**修法**:抵扣占用改条件更新:`UPDATE deduction SET ded_status='已抵扣', used_settle_bill_id=? WHERE id=? AND ded_status='待抵扣'`,受影响≠1 抛异常;结算单本身的`待确认→待付款`也用条件更新抢占。

11. **老板角色头前端硬编码**:`frontend/src/api/settle.ts:10`、`cashcheck.ts:99` 无条件送"老板"头,复选框只是 UI 闸(M1 stocktake 是 `opts.asBoss` 条件式)。SSO 前已知占位,建议至少拉齐成条件式。

## ✅ 做得好的地方

- **CashFlowWriter 包私有 + 事件唯一入口**:全系统确实找不到绕开单据直写 cash_flow 的路径(grep 验证 insert 只此一处);pl_line 只在写手内由枚举推导,"写入方不许自报去处"落实了。
- **pl_line 一一映射无旁路**:利润表全部行从 pl_line 聚合或 sale_record/盘亏单取数,NON_PL 毛额那笔既不进利润表也不重复进资产(现金=毛额−手续费=实际到账,核对无误);净损耗 = −损耗+赔付 的不重复计在行注里讲得清楚且实现一致。
- **mode_snap 防串单** + UNSET 三态门控(录入/确认/报表三层都拦)是教科书式防呆。
